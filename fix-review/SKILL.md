# Fix Code Review Comments

You are tasked with addressing code review comments from a GitLab merge request.

## Step 1: Fetch Unresolved Comments

Run the read-only fetch helper from inside the target repo. It resolves the project,
paginates all discussions, and prints only **unresolved** human inline review comments
(skipping resolved threads, system notes, and non-resolvable bot comments):

```bash
bash ~/.claude/scripts/fix-review/fetch-mr-comments.sh <MR_IID>
```

- `<MR_IID>`: extract from the argument URL if provided (e.g. `merge_requests/10113` → `10113`).
  Omit it to let the script infer the MR from the current branch.
- Output format per thread: a `DISC=<id> NOTE=<id>` line, then `[path:line] (author) body`,
  then any `↳` follow-up replies. The final line reports the count.

**Why a script:** all the `glab`/`python3` data-fetching lives inside the helper, so it runs
as a single allowlisted, read-only command — no per-step permission prompts. The script
performs **no** mutations (it never commits, replies, or resolves threads). If it fails,
fall back to `glab mr view -c` and filter manually.

**Filtering logic (implemented in the script):**
- `resolvable` — only inline code review comments are resolvable; general notes (bot summaries, MR descriptions) are not
- `resolved` on the first note — indicates whether the discussion thread is resolved
- Check the first note (not all notes) — resolution status lives on the first note of a discussion
- Skip `system` notes — these are auto-generated by GitLab (merge events, label changes, etc.)

## Step 2: Classify and Present Triage

Before fixing anything, classify each comment and present a checklist for approval:

```
Found N unresolved comments:

ACTIONABLE (code changes needed):
  1. [file.ts:45] "Use union type instead of OperationResult" (Tom Lokaj)
  2. [file.ts:89] "Missing null check on response" (Martin Safar)

QUESTIONS (need a response, not a code change):
  3. [file.ts:12] "Why not use X pattern here?" (Tom Lokaj)

SKIPPABLE (auto-generated or not actionable):
  4. [file.ts:33] GitLab Duo suggestion (GitLab Duo)

Proceed with fixing items 1-2? (Questions will be listed separately for you to answer)
```

**Classification rules:**
- **Actionable**: explicit change request, bug report, pattern violation, missing handling
- **Question**: asks "why", "what about", "have you considered" — needs a human answer, not a code change
- **Skippable**: GitLab Duo auto-suggestions, resolved-but-showing, praise/acknowledgment comments

Wait for user confirmation before proceeding.

## Step 3: Fix Actionable Items

For each actionable comment, in the order presented:

1. Read the relevant file and surrounding context
2. Understand the reviewer's intent (not just the literal words)
3. Make the change following project coding standards
4. If the fix is non-trivial or ambiguous, briefly explain your approach before making it

**Track all changes** as you go — you'll need this for the summary.

**If you hit a comment you're unsure about:** Don't guess. Flag it and move on. Present it at the end as "needs clarification".

## Step 4: Run Quality Checks

After all fixes are applied, run repo-specific quality checks.

**Discovery order:**
1. Check for a quality skill in the repo: `.claude/skills/*quality*` or `.claude/skills/*lint*`
2. If no skill, check `CLAUDE.md` for quality/lint/test commands
3. If nothing documented, detect from project files:
   - `build.gradle.kts` → `./gradlew build` (includes Spotless + Detekt for Kotlin repos)
   - `package.json` → check for `lint`, `typecheck`, `test` scripts → run them via `pnpm`
   - `pnpm run build` for TypeScript/npm packages

Fix any issues the quality checks surface (formatting, lint errors, type errors). These are separate from review comments — track them separately.

## Step 5: Commit and Push

Stage all changes and create a single commit:

```
ONE-XXXXX - address review feedback

Co-Authored-By: Claude Code <noreply@anthropic.com>
```

Extract the ticket ID from the branch name. If multiple rounds of review, increment: `address review feedback v2`, `v3`, etc.

Push to the existing branch.

## Step 6: Present Summary

```
## Review Feedback Summary

### Fixed (N items)
1. [file.ts:45] Used union type instead of OperationResult → changed return type to `CreateXResponse` union
2. [file.ts:89] Added null check on response → guard clause added at line 92

### Questions for You to Answer (N items)
3. [file.ts:12] "Why not use X pattern here?" — reviewer is asking about <context>. Your call.

### Skipped (N items)
4. [file.ts:33] GitLab Duo auto-suggestion — skipped

### Quality Check Fixes (if any)
- Fixed Spotless formatting in 2 files
- No test failures

### Needs Clarification (if any)
- [file.ts:120] "Consider refactoring this" — unclear what specific change is wanted

Committed and pushed as `abc1234`.
```

## Step 7 (Optional): Resolve Threads

After the summary, offer:

```
Would you like me to resolve the N addressed threads on GitLab?
```

If yes, resolve each thread via API (`:fullpath` resolves the current repo automatically;
`$DISCUSSION_ID` is the `DISC=` value from Step 1, `$MR_IID` is the MR you're working on):
```bash
glab api -X PUT "projects/:fullpath/merge_requests/$MR_IID/discussions/$DISCUSSION_ID" -f resolved=true
```
This is a **mutation** and will prompt for approval — that is intended.

Only resolve threads that were actually fixed with code changes — never resolve questions or skipped items.

## Important Notes

- Be thorough — don't skip actionable comments
- If a comment is unclear, flag it as "needs clarification" rather than guessing
- Maintain code quality and consistency with the existing codebase
- Never resolve threads without explicit user approval
- One commit for all fixes (not per-comment commits)
